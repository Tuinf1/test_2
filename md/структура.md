# Анализ возможности взаимозачёта

## 1. Цель

Нужно подготовить помощника финансовому контролёру, который:

1. получает сведения о дебиторской задолженности (ДЗ), просроченной дебиторской задолженности (ПДЗ) и кредиторской задолженности (КЗ);
2. находит встречные требования по одному контрагенту;
3. определяет возможность полного или частичного зачёта;
4. показывает, между какими ДО, договорами и суммами возможен зачёт;
5. сохраняет результат в Excel.

Для текущего MVP достаточно Python и `openpyxl`. SQL и нейронная сеть для примера на 100 строк не требуются.

## 2. Термины

- **ДО** — внутригрупповое (дочернее) общество.
- **Контрагент** — сторонняя организация.
- **ДЗ** — контрагент должен ДО.
- **ПДЗ** — просроченная ДЗ.
- **КЗ** — ДО должно контрагенту.
- **Двусторонний зачёт** — встречные требования между одним ДО и контрагентом.
- **Трёхсторонний зачёт** — одно ДО должно контрагенту, а контрагент должен другому ДО.

Пример трёхстороннего зачёта:

```text
ДО1 должно К/а 1: 51
К/а 1 должен ДО2: 111
Возможный зачёт: 51

После зачёта:
КЗ ДО1: 0
ДЗ ДО2: 60
```

## 3. Первичные данные

Текущий входной файл: `задолженность.xlsx` в корне проекта.

Лист: `Данные`.

Фактический объём примера:

- 100 строк данных;
- 10 ДО;
- 10 контрагентов;
- по одной строке на сочетание ДО и контрагента.

Столбцы:

| Столбец | Значение |
|---|---|
| `ID` | Уникальный номер исходной позиции |
| `ДО` | Внутригрупповое общество |
| `Контрагент` | Сторонний контрагент |
| `Договор` | Договор, к которому относится задолженность |
| `Вид ДЗ` | `ПДЗ` или обычная `ДЗ`; относится только к дебиторской задолженности |
| `Сумма ДЗ` | Сумма, которую контрагент должен ДО |
| `Сумма КЗ` | Сумма, которую ДО должно контрагенту |

Файл `генерация_данных.py` создаёт тестовый файл `задолженность.xlsx`.

## 4. Что уже реализовано

### Этап 1. Представление по ДО

Python-файл: `функции/1_промежуточная таблица.py`.

Вход:

```text
задолженность.xlsx
```

Выход:

```text
Промежуточная таблица 1.xlsx
```

Листы результата:

| Лист | Назначение |
|---|---|
| `Данные` | Первичные данные без потери исходных строк |
| `1_ДО` | Те же позиции, сгруппированные по ДО |

Лист `1_ДО` нужен для просмотра задолженности со стороны каждого внутригруппового общества: кто должен ДО и кому должно само ДО.

### Этап 2. Представление по контрагентам

Python-файл: `функции/2_функция_2_вторая.py`.

Вход:

```text
Промежуточная таблица 1.xlsx
```

Выход:

```text
Промежуточная таблица 2.xlsx
```

Листы результата:

| Лист | Назначение |
|---|---|
| `Данные` | Сохранённые первичные данные |
| `1_ДО` | Сохранённое представление по ДО |
| `2_Контрагент` | Позиции, сгруппированные по контрагенту |

Лист `2_Контрагент` нужен для визуального поиска встречных ДЗ и КЗ внутри одного контрагента.

Столбцы `Остаток ДЗ` и `Остаток КЗ` на этом этапе являются начальными остатками до зачёта и равны исходным суммам.

## 6. Расчёт взаимозачёта, который нужно реализовать дальше

Расчёт следует выполнять по первичным строкам листа `Данные`. Форматированные листы `1_ДО` и `2_Контрагент` предназначены для просмотра; разбирать их заголовки, пустые строки и строки `Итого` для расчёта не нужно.

Для каждого контрагента:

1. Выбрать позиции, где `Сумма ДЗ > 0`.
2. Выбрать позиции, где `Сумма КЗ > 0`.
3. Для выбранной пары рассчитать:

   ```text
   сумма зачёта = min(остаток ДЗ, остаток КЗ)
   ```

4. Уменьшить остаток ДЗ и остаток КЗ на сумму зачёта.
5. Записать отдельную операцию с указанием исходных `ID`, ДО, договоров, вида ДЗ и суммы зачёта.
6. Повторять подбор, пока у контрагента одновременно остаются ДЗ и КЗ.
7. Если встречной стороны нет, указать причину:
   - `Нет ДЗ для зачёта`;
   - `Нет КЗ для зачёта`;
   - `Задолженность отсутствует`.

Если ДО в строке ДЗ и строке КЗ совпадает, это двусторонний зачёт. Если ДО различаются, это трёхсторонний зачёт.

## 7. Предлагаемый итоговый файл

Следующий скрипт должен открыть `Промежуточная таблица 2.xlsx`, сохранить существующие листы и создать новый файл:

```text
Результат взаимозачёта.xlsx
```

Листы итоговой книги:

| Лист | Содержание |
|---|---|
| `Данные` | Первичные данные |
| `1_ДО` | Представление по ДО |
| `2_Контрагент` | Представление по контрагентам до зачёта |
| `3_Результат` | Предлагаемые зачёты, отсутствие зачётов и конечные остатки |

На листе `3_Результат` достаточно трёх разделов.

### 7.1. Возможные зачёты

| Поле | Для чего нужно |
|---|---|
| `№` | Номер операции |
| `Контрагент` | Контрагент, внутри которого найдено встречное требование |
| `Вид зачёта` | Двусторонний или трёхсторонний |
| `ID КЗ` | Исходная строка кредиторской задолженности |
| `ДО с КЗ` | ДО, которое должно контрагенту |
| `Договор КЗ` | Договор кредиторской задолженности |
| `ID ДЗ` | Исходная строка дебиторской задолженности |
| `ДО с ДЗ` | ДО, которому должен контрагент |
| `Договор ДЗ` | Договор дебиторской задолженности |
| `Вид погашаемой ДЗ` | ПДЗ или обычная ДЗ |
| `Сумма зачёта` | Возможная сумма зачёта |
| `Остаток ДЗ` | Остаток выбранной позиции ДЗ после операции |
| `Остаток КЗ` | Остаток выбранной позиции КЗ после операции |

Каждая пара требований записывается отдельной строкой. Если одна КЗ закрывает две позиции ДЗ, в результате должны быть две операции.

### 7.2. Контрагенты без зачёта

| Поле | Для чего нужно |
|---|---|
| `Контрагент` | Контрагент без встречных требований |
| `Общая ДЗ` | Сумма ДЗ по контрагенту |
| `Общая КЗ` | Сумма КЗ по контрагенту |
| `Причина` | Почему зачёт не найден |

### 7.3. Незакрытые остатки

Следует показать исходный `ID`, ДО, контрагента, договор, вид ДЗ и остаток, который не удалось закрыть зачётом.

## 8. Правила, которые подтверждены заданием

- Анализ выполняется по стороннему контрагенту.
- Нужно учитывать ДЗ, ПДЗ и КЗ.
- Допускается полное и частичное погашение.
- Нужно показать возможность двух- и трёхстороннего зачёта.
- Результат предоставляется в табличном формате Excel.
- Исходные данные для тестового примера можно сформировать самостоятельно.

## 9. Вопросы, которые задание не определяет

Эти правила нельзя считать утверждёнными без отдельного решения:

1. Нужно ли сначала погашать ПДЗ, а затем обычную ДЗ.
2. В каком порядке выбирать несколько договоров: по `ID`, дате, сроку просрочки или сумме.
3. Можно ли выполнять зачёт внутри одного ДО или нужны только разные ДО.
4. Какие признаки подтверждают однородность требований.
5. Нужно ли учитывать валюту, дату возникновения, срок оплаты, спорность и юридические ограничения.

В текущих данных нет валюты и юридических признаков однородности. Поэтому MVP может только находить **кандидатов на зачёт по одному контрагенту**, а не подтверждать юридическую допустимость зачёта.

До согласования порядка расчёта безопаснее сохранять исходный порядок строк и явно указывать это как техническое поведение, а не как бизнес-правило.
